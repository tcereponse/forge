 React Forge — Guide Complet
📋 Vue d'ensemble
React Forge est un générateur de projets React par IA qui crée des applications complètes, fonctionnelles et téléchargeables. Il génère le code source, installe les dépendances, compile le projet, affiche un aperçu en direct, et produit un template Android APK.

1. 🏗️ Création de Projet
Description
L'utilisateur décrit son application en langage naturel
Ou laisse vide — une description est auto-générée à partir des features et packs sélectionnés
Plus la description est précise, meilleur est le code généré
Stack technique configurable
Option
Choix
Build tool	Vite + React, Next.js, Create React App
TypeScript	Activé/désactivé
Styling	Tailwind CSS, CSS Modules, Styled Components
Routing	React Router v6 (HashRouter), Aucun
State management	Aucun, Zustand, React Context, Redux Toolkit
UI Library	Aucune, shadcn/ui, Material UI

Fonctionnalités (10 disponibles)
Chaque feature est vraiment implémentée dans le code (pas juste un commentaire) :

🌙 Dark Mode — toggle avec classList.toggle('dark') + classes dark: Tailwind
🔐 Authentification — formulaire login/logout avec useState
🌐 Couche API / fetch — fonctions fetch avec loading/error states
📝 Formulaires — react-hook-form avec validation Zod
📊 Graphiques — recharts (BarChart, LineChart) avec données mockées
📋 Tableaux — tableau HTML triable avec pagination

🧪 Tests — Vitest + @testing-library/react + fichier de test
✨ Animations — framer-motion (motion.div, AnimatePresence, whileHover)

3. ⚙️ Génération (4 phases)
Phase 1 : Arsenal PRD Grade Diamond (10 documents)
L'IA génère 10 documents PRD structurés qui guident la génération :

Vision Stratégique — objectifs, public, fonctionnalités clés
Architecture Système — stack, structure des dossiers
Interface Utilisateur — design system, composants
Base de Données — modèles de données, schémas
Sécurité — auth, validation, guards
API et Protocoles — endpoints, hooks de fetch
Expérience Utilisateur — animations, empty states
Tests et Qualité — stratégie, cas de test
Déploiement — build Vite, optimisations
Maintenance — roadmap, monitoring
Phase 2 : Génération de code
L'LLM génère les fichiers React (App.tsx, MainComponent.tsx, composants pack)
Le prompt inclut les directives UI par pack, l'arsenal PRD, les contextes d'extensions
Règle stricte : chaque composant doit avoir une VRAIE UI (pas de stub)
Navigation fonctionnelle : tous les boutons ont un onClick
Phase 3 : Templates + Fusion
Fichiers de config injectés déterministiquement : package.json, vite.config, tsconfig, tailwind.config, postcss.config, index.html, main.tsx, .gitignore, README.md
Fichiers mobile : manifest.json, sw.js, icon.svg, capacitor.config.ts, BUILD_APK.md
Phase 4 : Post-traitement
Anti-corruption : détection et réparation des sauts de ligne \n → newline
Réconciliation des dépendances : scan des imports → ajout auto au package.json
Auto-réparation des imports manquants : si l'LLM importe un composant qu'il n'a pas créé, un 2ème appel LLM génère le composant manquant
Création de stubs : fallback si l'auto-réparation échoue
Vérification : config Tailwind, utils.ts/cn(), architecture React

Phase 3 — Intégration dans le Core (Semaine 6-7)
Objectif

Changements
typescript

// packages/core/workflow/generate-workflow.ts
class GenerateWorkflow {
  constructor(
    private prdGenerator: IPrdGenerator,
    private codeGenerator: ICodeGenerator,
    private repairEngine: IRepairEngine,
  ) {}

  async execute(config: ProjectConfig): Promise<Project> {
    // 1. Check GPU capabilities
    const caps = await this.aiService.getCapabilities();
    
    // 2. Generate PRD (GPU if available)
    const arsenal = await this.prdGenerator.generate(config, packs);
    
    // 3. Generate code (GPU if available)
    const files = await this.codeGenerator.generate(prompt, config);
    
    // 4. Repair (GPU or CPU)
    const repaired = await this.repairEngine.repair(files, issues);
    
    // 5. Build & validate (CPU only)
    await this.buildRunner.build(projectId);
    
    return project;
  }
}

5. 🔄 Gestion des Fallbacks
Scénarios de fallback
text

Scénario 1: GPU disponible et fonctionne
    → TensorRT-LLM utilisé
    → Latence: 1-2s
    → Badge: 🟢 GPU

Scénario 2: GPU disponible mais OOM (mémoire pleine)
    → Erreur GPU détectée
    → Bascule automatique vers CPU
    → Latence: 8-15s
    → Badge: 🟡 CPU (GPU OOM)
    → Log: "GPU OOM, fallback CPU activé"

Scénario 3: Pas de GPU NVIDIA
    → Détection: pas de CUDA/TensorRT
    → Utilise z-ai-web-dev-sdk (cloud)
    → Latence: 30-60s
    → Badge: 🟡 Cloud

Scénario 4: Service GPU indisponible
    → Timeout sur /v1/health
    → Bascule vers z-ai-web-dev-sdk
    → Latence: 30-60s
    → Badge: 🟡 Cloud (service GPU down)

Scénario 5: Mode Electron sur PC avec GPU
    → Service GPU lancé automatiquement
    → Modèle chargé en mémoire
    → Pas de cold start
    → Latence: 1-2s
    → Badge: 🟢 GPU (Electron)
